# Running this stack under sparkrun

The repo's canonical flow is a3refaat's `run-recipe.sh` / `launch-cluster.sh`
(see [`../DEFAULT-CONFIG.md`](../DEFAULT-CONFIG.md)). This directory is a port of
**lane A — BALANCED**, the verified hero config, to
[sparkrun](https://github.com/spark-arena) so the same serve line can be driven
by `sparkrun run` against a named 2-node cluster.

| file | what it is |
| --- | --- |
| [`minimax-m3-w4a16-gptq-b12x-nvfp4-eagle3.yaml`](minimax-m3-w4a16-gptq-b12x-nvfp4-eagle3.yaml) | the sparkrun recipe (schema v2). Header carries the full prerequisite/launch/port notes. |
| [`sync-mods.sh`](sync-mods.sh) | stages the 9 mods the recipe needs into `./mods/` from a3refaat's branch, and applies the graceful-skip patch |
| `mods/` | generated by `sync-mods.sh`, gitignored — a3refaat's MIT mods, not re-vendored here |

## What sparkrun does for you, and what it doesn't

**Does:** distributes the container image to the worker (`docker save | ssh
docker load`) and rsyncs the HF model cache to every node — i.e. steps 2 and 3
of `../DEFAULT-CONFIG.md` are automated, for **both** the 224G target and the
1.6G EAGLE3 drafter. (The drafter is listed explicitly in the recipe's
`distribution_config`; sparkrun's auto-detection misses it because this recipe
carries its spec config inline in the command rather than as a
`speculative_config` default. Since the vLLM runtime forces `HF_HUB_OFFLINE=1`
in the containers, a missing drafter is a hard failure at draft-model load, not
a slow first boot — do not delete that stanza.) Also handles container lifecycle,
native multi-node coordination (`--nnodes/--node-rank/--master-addr/
--master-port/--headless`, the same thing `--no-ray` does upstream),
`VLLM_HOST_IP` pinning to the chosen fabric, and health-gated post hooks.

**Doesn't:** build the image. There is no published `vllm-node-minimax-m3-b12x`
— it must be built from a3refaat's patched checkout on the head node.

## Full flow, cold start

```bash
# 1. Build the image on the HEAD node (once; ~29G, 1-2h cold)
git clone -b minimax-m3-4bit-w4a16 https://github.com/a3refaat/spark-vllm-docker.git
cd spark-vllm-docker                                    # branch HEAD f942437
git apply <this-repo>/patches/dockerfile-unreachable-ref-fetch.patch
git apply <this-repo>/patches/mod-prometheus-graceful-skip.patch
./build-deploy.sh
cd -

# 2. Stage the mods next to the recipe
./sparkrun/sync-mods.sh --src ../spark-vllm-docker      # or omit --src to clone

# 3. Sanity-check the port before touching hardware
sparkrun recipe validate ./sparkrun/minimax-m3-w4a16-gptq-b12x-nvfp4-eagle3.yaml
sparkrun run ./sparkrun/minimax-m3-w4a16-gptq-b12x-nvfp4-eagle3.yaml \
    --cluster fabric --tp 2 --dry-run

# 4. Launch. sparkrun distributes the image + the 224G/1.6G weights itself.
sparkrun run ./sparkrun/minimax-m3-w4a16-gptq-b12x-nvfp4-eagle3.yaml \
    --cluster fabric --tp 2

# 5. Stop (the --tp 2 must be repeated — it is part of the workload identity)
sparkrun stop ./sparkrun/minimax-m3-w4a16-gptq-b12x-nvfp4-eagle3.yaml \
    --cluster fabric --tp 2
```

### Which cluster

On the reference lab (`gb10-spark` + `gx10-spark`) there are two definitions of
the same pair, and for this workload you want the fabric one:

| cluster | hosts | use |
| --- | --- | --- |
| `default` | 10.10.20.10/.11 (management, via switch) | general use; NCCL still moves bulk traffic over the RoCE HCAs |
| `fabric` | 10.99.10.10/.11 (`enp1s0f1np1`, 200 Gb/s RoCE) | **this recipe** — `transfer-interface: cx7`, so the 224G weight rsync and the 29G image copy ride the 200G link instead of the management NIC |

At 224G of weights the staging difference is minutes versus a long wait, and it
matches how the 36.6 tok/s reference pair was wired.

### A note on the scheduler

The recipe sets `scheduler: greedy` deliberately. Under `occupancy-sparse` (the
0.3.x default for new clusters) the VRAM estimate becomes a hard admission
check, and this model's estimate is wrong in the direction that refuses the
launch outright — `Cluster cannot satisfy 2 ranks ... only placed 0 of 2`. No
cluster-wide `--max-gpu-mem-util` fixes it: the inflated figure is 115.2 GB per
rank against a 121 GB accelerator, so even a 0.93 cap (112.5 GB usable) still
refuses. `greedy` places the ranks and lets vLLM's own memory profiler — which
knows the real MSA KV geometry — be the authority. This is per-recipe and does
not weaken placement for anything else on the cluster.

Run it **by file path**: a locally-sourced recipe is auto-trusted, so its mods
(injected as `pre_exec` hooks) run without a per-launch confirmation prompt.
Installing it into an untrusted registry makes every launch prompt —
`sparkrun registry trust <name>` if you'd rather have it discoverable by name.

## Things that will bite you

These are the upstream gotchas that survive the port. The full list, with error
signatures, is in [`../DEFAULT-CONFIG.md`](../DEFAULT-CONFIG.md).

1. **The mods are not optional and neither is the graceful-skip patch.**
   `sync-mods.sh` applies it. Without it the prometheus mod's anchor misses on
   prometheus-fastapi-instrumentator 8.0.2 and, because mods run under
   `set -euo pipefail`, the whole launch aborts.
2. **`gpu_memory_utilization` is a knife-edge.** 0.929 on the reference pair;
   0.93 failed the startup free-memory check by 0.02 GiB and 0.925 shrank the KV
   pool below what 196K context needs. Bracket it on your own boot state —
   both failure modes print the exact number you need. `--gpu-mem 0.925`
   overrides without editing the recipe.
3. **Ignore sparkrun's VRAM warning.** The estimator charges 4 KV heads across
   all 60 layers; MiniMax-M3's MSA layers carry 2, and the per-host `[EXCEEDS]`
   line assumes 85% utilization rather than this recipe's 0.929. Measured
   reality is a 208,128-token pool. Do not lower `max_model_len` because of it.
4. **Never benchmark the first request** — it pays the ~60s b12x JIT warmup.
   The recipe's `post_commands` burns one warmup request after the health gate,
   but burn one more per *workload shape* before recording numbers.
5. **NCCL stays stock.** `NCCL_PROTO=LL` + `NCCL_MAX_NCHANNELS=2` loses 5-9% on
   this model even though it wins on 32B-class dense models on the same fabric.
6. **Weights are gated by the license, not just by size.** MiniMax-M3 is under
   the MiniMax Community License (non-commercial constraints), independent of
   this repo's code license. Export `HF_TOKEN` on the control machine — the
   recipe passes it through as `${HF_TOKEN}`.

## Lanes B and C

Only lane A is ported. Lanes B (`kvarn`, drafterless, 262K context) and C
(`kvarn-eagle3`, 131K, max throughput) are *easier* to port than lane A was:
their yamls in [`../recipes/`](../recipes/) already list their mods explicitly
instead of through a group, so the `mods:` block copies over as-is (drop the
`mods/` prefix, which sparkrun strips anyway). They drop the four b12x mods and
add `add-kvarn-kv-quant`, `fix-minimax-m3-kvarn-sparse`,
`fix-minimax-m3-kvarn-indexer`, `fix-kvarn-dense-fa-scratch-cap`, and
`fix-cudagraph-mem-profile-double-charge`; lane C additionally keeps
`fix-eagle3-draft-embed-quant` and adds `fix-eagle3-drafter-pagecache`. Note
`fix-minimax-m3-kvarn-hybrid` exists upstream but neither lane uses it —
kvarn-sparse replaces it and they must not be combined.

`kv_cache_dtype` becomes `kvarn_k4v2_g128` and `attention_backend` leaves b12x.
To port: copy this recipe, swap the `mods:` list and the serve flags from the
corresponding `../recipes/` yaml, and extend `sync-mods.sh`'s `MODS` array.
Lane C's yaml also predates the safetensors switch and still carries
`load_format: instanttensor`, under which the page-cache rules in
`../DEFAULT-CONFIG.md` are fatal if ignored.

## Verified / not verified

- **Verified here:** `sparkrun recipe validate` passes; `--dry-run` against a
  2-node cluster resolves all 9 mods, renders the serve command byte-equivalent
  to lane A's verified line, and plans image + model distribution to both hosts.
- **Not verified here:** an actual boot. The image was not built and the 224G
  weights were not staged on this machine. The 36.6 tok/s figure comes from a
  direct-cabled 200G RoCE pair; on a switched fabric the MoE all-reduce cost
  differs and throughput is unknown until you measure it.
