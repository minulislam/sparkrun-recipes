## 3. sparkrun 0.3.10 defects found (both silent)

### 3.1 Self-rsync destroys symlinked HF blobs — data loss

When the control machine is itself a cluster member (our head), `models/distribute.py:
distribute_model_from_local` rsyncs the model to **every** host, including itself through its
own CX7 address (`10.99.10.10`), with `-a --size-only --mkpath --partial --links
--copy-unsafe-links`. Recent huggingface_hub (the pipx `hf` CLI) keeps bytes in a cache-wide store
`hub/blobs/xx/<key>` and makes each per-model `blobs/<sha256>` a **symlink** into it. On a
same-directory rsync `--copy-unsafe-links` turns each symlink into "a regular file to receive";
the receiver unlinks the symlink a moment before the sender opens it:

```
Rsync <- 10.99.10.10 FAILED rc=24 (0.5s): file has vanished: ".../models--local-inference-lab--Qwen3.8-Flash-Next-NVFP4/blobs/0997f410…"
```

Every weight shard of both Flash-Next models vanished from head *and* worker (the worker only ever
received the dangling skeleton); the 13 small regular files survived. Reproduced with
`rsync -n --itemize-changes` on an intact model: every symlinked blob is listed `>f+++++++++`.
Models whose blobs were regular files (everything downloaded with the older `huggingface-cli`)
were untouched, which is why every earlier TP2 launch was fine.

**Recovery.** The bytes were still in `hub/blobs/`. `relink_scan.py` (job tmp) fetched each repo's
tree from the Hub (`lfs.oid` = the per-model blob name), size-matched store files, sha256-hashed
57 candidates (289 GB) and matched 57/57. Each `blobs/<oid>` was recreated as a **hardlink** to the
store file (same inode, zero extra space, and rsync sees a regular file). Laguna, nvidia/Qwen3.8-27B
and the Inkling DSpark draft still had symlinked blobs and were converted the same way. The dry-run
rsync now transfers nothing. Worker re-synced head→worker with sparkrun's own flags: 105.8 + 183.5
+ 1.8 GB, `dangling=0`.

**Rule:** after any `hf download` on the head, hardlink the per-model blobs before a TP2 launch
(see memory note `sparkrun-0310-distribution-bugs`). Upstream fix: skip `is_local_host` targets in
`distribute_model_from_local`, or never use `--copy-unsafe-links` when source host == target host.

### 3.2 Digest-pinned `container:` images do not survive save|load

`container: scitrera/dgx-spark-sglang-mm@sha256:9a6e…` is shipped to the worker with
`docker save | docker load`, which strips `RepoDigests`. On the worker the image exists only as an
untagged ID; rank-1 `docker run <repo>@sha256:…` fails "No such image" (docker events show only
`image load`, never `container create`), sparkrun still reports "Step 7/7: Starting worker nodes —
done", the head waits at "Init torch distributed begin", and readiness eventually reports
"head container is not running". Fix: reference a tag (tags survive save|load) and record the
digest in a comment. The AEON digest recipes only work because that image was pulled on the
worker directly at some point.

## 4. The "exit 137 at ~4 min" deaths — resolved

`docker events` showed `kill SIGTERM → kill SIGKILL → stop → die 137 → destroy` with memory
healthy, and sparkrun's auto-remove had erased the logs. The stop came from **Spark Studio**
(`~/spark-studio`, `spark-studio.service`, :7861): it adopts every sparkrun job as a run, its
watchdog notices when the serve process dies inside the container, and it runs `sparkrun stop`
plus a `drop_caches` reclaim (`[watchdog] serve process died inside the container — tearing the
zombie container down`). It is a janitor, not a killer — but its per-run ring buffer
(`GET /api/runs/<id>/tail`) is the only place the engine tracebacks survived. They were:

| Run | Root cause (from the engine) | Fix |
|---|---|---|
| Laguna, pass 3 | `Free memory on device cuda:0 (66.64/121.69 GiB) on startup is less than desired GPU memory utilization (0.9, 109.52 GiB)` — ollama's gemma4:31b was resident (see co-tenant below). | Benchmark driver now waits for `ollama ps` to be empty. |
| Laguna, pass 3b (no co-tenant) | `To serve at least one request with the model's max seq len (262144), 12.35 GiB KV cache is needed, larger than the available 10.22 GiB` — the weights are 99.7 GB on disk (48-layer/256-expert MoE), not the card's "30B". | `max_model_len` 262144 → 131072. |
| Flash-Next base (`@eugr` cluster) | `io_uring bounce initialization failed: Operation not permitted` in WorkerProc init — the b12x loader needs io_uring, rootless Docker's seccomp forbids it. | Local copy `qwen3.8-flash-next-nvfp4-tp2.yaml` with `load_format: safetensors` + readiness block. |
| Flash-Next uncensored | same io_uring failure | `load_format: safetensors`. |
| DeepSeek coder | `7.19 GiB KV cache is needed` vs the 6 GiB `kv_cache_bytes` cap | cap → 12 GiB. |
| Laguna, pass 5 (131k ctx, 0.90 util) | Loaded 93.21 GiB in 644 s, KV check passed (275,742 tokens), then NVRM `NV_ERR_NO_MEMORY` and **earlyoom SIGTERM at 1.98 % available** — 0.90 × 121.69 GiB plus the 6.5 GB engine RSS is the whole node. | `gpu_memory_utilization` → 0.85. |
| Flash-Next uncensored, pass 5 (PLE in RAM) | `ValueError: Invalid layer_type qwen_sparse_attention` — orcarouter's config.json uses the newer transformers name for the 12 QSA layers; the eugr image's `qwen4_exp/nvidia/model.py` only knows `full_attention` (+ `indexer_n_heads` ⇒ QSA). Also: this checkpoint keeps the per-layer-embedding table in **bf16** (the 102 GB shard), so `VLLM_PLE_TABLE_MEMORY=ram` maps **47.68 GiB per rank of host memory**; the base local-inference-lab checkpoint quantized it to nvfp4 and needs neither. | `--hf-overrides` remapping the 12 layers to `full_attention`; `gpu_memory_utilization` 0.82 → 0.50 to leave room for the mapped table. |

Note on Spark Studio: its pre-launch memory guard *will* stop any resident sparkrun job when
someone launches a model through its UI (`[guard] stopping running model … to free unified
memory`). Nothing of the sort happened today, but it is a second co-tenant path to remember.

## 4b. MiniMax-M2.7 NVFP4 EP=2 on the Atlas engine (`@atlas` registry) — verified

`sparkrun registry update atlas` — the cached index was stale) found
`@atlas/minimax-m2.7-nvfp4-ep2`: Atlas's pure-Rust/CUDA engine, tp=1 / ep=2 across the pair,
`lukealonso/MiniMax-M2.7-NVFP4` (134.5 GB, on both nodes). It validates but does not run as
published; every step below was measured, and the result lives in
`recipes/minimax-m2.7-nvfp4-atlas-ep2.yaml` (a documented fork).

## 5. Open items

- **SGLang TP2 hang** (minimax): both ranks reach "CustomAllreduce is disabled because this process
  group spans across nodes", then 29 min of silence, 0 MB/s reads, 3 GB RSS, port never opens.
  Try `--load-format auto`, `NCCL_DEBUG=INFO`, py-spy inside a `--no-rm` container. Inkling
  (also SGLang TP2) may hit the same wall.
- **step37 coherence failure**: reproduce with curl, try `kv_cache_dtype: auto` and
  `--dtype bfloat16`; check the AEON image's Step3p7 support notes.
- **Co-tenant from the memory gateway — RESOLVED 2026-09-27 ~14:00.** The LiteLLM gateway on
  10.10.20.40 was calling this head's ollama (`gemma4:31b`, ~46 GB of unified memory while loaded,
  ~30-min cadence plus bursts); it cost Laguna pass 3 its startup budget and confounded the first
  worker reset. `gemma4:31b` on the head is now an alias of the **cloud** model, so gateway traffic
  loads nothing locally. Pass 5 ran start-to-finish with `ollama ps` empty; the driver keeps the
  gate as belt-and-braces (`nomic-embed-text` still parks 323 MB briefly).
- **DeepSeek coder's 8k-depth cell kills the worker node — reproduced WITHOUT the co-tenant.**
  Occurrence 1, 08:38: worker journal stops mid-line at 08:35:07, no shutdown sequence, boots clean
  3 min later; blamed on the concurrent ollama burst. Occurrence 2, pass 5 at 15:35 with ollama
  empty: depth-0 cells fine (29.9 c=1 / 55.5 8-way), then during the d=8192 cells the head rank
  logged 60-s `shm_broadcast` stalls (its TP peer gone) and gx10-spark went dark for **53 minutes
  without rebooting**. The worker's own journal has the whole anatomy: 15:31:17 NVRM
  `NV_ERR_NO_MEMORY`; 15:31:18 onward earlyoom SIGTERMs `VLLM::Worker_TP` dozens of times —
  the process sheds RSS (3067 → 236 MiB) but **never exits** (stuck in the driver, SIGTERM
  ineffective, and earlyoom never escalates); mem-avail bottoms at **70 MiB (0.06 %)**; the journal
  is silent 15:37:47 → 16:24:45 (userspace livelocked: ping and TCP-accept still answered, sshd
  couldn't fork a banner); at 16:24 the process finally died and the node recovered on its own.
  The common factor with occurrence 1 is the 8k prefill transient: `max_num_batched_tokens: 8192`
  chunks through b12x MoE + dspark speculative + FULL cudagraphs on ranks already at ~6 %
  host-available. **FIXED in pass 6**: `-o max_num_batched_tokens=2048` (the MiniMax §4b
  bounded-prefill fix) completed all six cells with no incident; the recipe now carries 2048.
- **The worker wedges again on teardown.** Minutes after the successful pass-6 DeepSeek run was
  stopped (17:17), gx10-spark re-entered the same state: ping and TCP-accept answer, sshd sends no
  banner. Zero sparkrun containers were left anywhere sparkrun could see. Working hypothesis from
  both incidents: force-removing (or OOM-reaping) a b12x rank with ~80 GiB of pinned unified memory
  puts the NVIDIA UVM cleanup into a long D-state storm that starves userspace for 30–60 min; the
  15:31 livelock recovered by itself at 16:24 the same way. Watch for recovery rather than
  power-cycling. Consider `sparkrun stop` → in-container graceful `kill -TERM` of the serve process
  first, or a delay between benchmark end and stop.
- **Flash-Next uncensored remains the one unrun recipe — new, different failure in pass 6.** Rank 0
  (head) now gets past everything that killed passes 3–5: safetensors loader ok, layer remap ok,
  PLE-in-RAM ok, **40.11 GiB loaded in 343 s**, mamba/attention page sizing logged — then the gloo
  `in_the_same_node_as` barrier died with "Connection closed by peer [10.99.10.11]" because the
  WORKER rank exited first. The worker container auto-removed, so its traceback is lost, and the
  node wedged (bullet above) before its journal could be read. Next attempt: launch with
  `--no-rm` (or `sparkrun run` + manual probe) and read rank 1's `/tmp/sparkrun_serve.log`;
  suspect the worker-side PLE bf16 table (47.68 GiB host map) or a gated-repo/token difference
  on the worker.
